## 1. Порог мощности проплава (совещательный)
ПРОБЛЕМА: реальный валик — 160 Дж/мм при медленном C дали ~10.5 мА = ~630 Вт и
непроплав/шарики; override ×2 (~21 мА = 1.26 кВт) дал проплав. Приложение молчало.
ПРИЧИНА: Дж/мм не гарантирует проплав — при низкой скорости «правильная» энергия
даёт малую абсолютную мощность P=U·I. Формула тока верна; мала цель для этой скорости.
БЫЛО: только current_low_warning_ma (1 мА) — не ловит 630 Вт.
СТАЛО: min_beam_power_w=900 (0=выкл) + power_floor_warning_enabled;
beam_power_floor_analysis() в audit_report (единая точка всех 6 генераторов):
ключи stats, предупреждение с числами (какая энергия/ток/скорость нужны), раздел
"Beam power (fusion) check" в аудите; поле в UI; баннер после генерации; строка в сводке.
G-code НЕ меняется, ток НЕ поднимается, overrides не трогаются.
ЗАВИСИМОСТИ: audit_report — все генераторы получают проверку автоматически.
ТЕСТ: реальные настройки пользователя (ebam_settings_v4291_FULL.json) → 519–628 Вт,
предупреждение срабатывает; подсказка 229 Дж/мм / 15 мА к порогу при текущей скорости.

## 2. Задача «Калибровка валиков (TEST)»
ПРОБЛЕМА: порог 900 Вт — стартовая оценка; реальный порог машины определяется валиками,
а подбор шёл override'ом вслепую.
СТАЛО: generate_calibration_beads() — матрица валиков (строки=токи, столбцы=скорости),
через проверенный безопасный эмиттер (нет G0 под лучом, баланс W, M68-только, без M49/M50);
комплект .ngc + карта CSV + аудит. analyze_calibration_results() — по измерениям
(ширина/высота/проплав) считает: порог мощности (вилкой из данных), Z-шаг (медианная
высота), шаг TOM 0.738w / FOM 0.667w, целевую энергию, оценку η (сверяется с массовой
калибровкой v4.2.9.9). Противоречия помечаются; η>1 ловится как ошибка измерения.
ТЕСТ: матрица 5×3: audit ok, g0=0, w_final=-0.8, Bormash OK, M67=0, M49/M50=0.
На реальных точках пользователя: порог 941 Вт (вилка 628..1254), энергия 319 Дж/мм —
совпадает с ручным расчётом (~900 Вт / ~320 Дж/мм) и с override-экспериментом.

## 3. Контекстная таблица «Расчётные значения» (запрошенная задача)
ПРОБЛЕМА: всегда 33 строки; в XY-режиме видны C-строки с «—», в C-режиме — лишние
hatch-строки; сбивает с толку.

СТАЛО: _build_calc_rows() — строки добавляются по контексту: C-блок только при
c_limit_info; «Переход C+Z» только в no-pause; лимитер/клип/цель-энергия/контроль
подачи/контур/перемычки/доп.время — только когда реально действуют. Новая строка
«Мощность пучка (порог)». ПОПУТНО ИСПРАВЛЕН DISPLAY-БАГ: объёмная энергия в сводке
делилась на hatch_spacing даже в C/кольцевых режимах — теперь на
_effective_rotational_radial_step (как считает ядро).
ТЕСТ (AST-извлечение билдера, 4 сценария + числа): XY чистый = 13 строк (C/лимитер/
контур отсутствуют); C no-pause с лимитом = 25 (всё нужное есть, лишнего нет);
C отдельные кольца = 18 (без «Переход C+Z» и лимитера); клип тока/порог E0/проволока
у максимума = 18 (строки появились). Числовая сверка: 160 Дж/мм, слой 0.5, рад.шаг 2.5
→ показ 128.0 Дж/мм³ (по шагу), а не 160.0 (старое, по hatch — неверно).
